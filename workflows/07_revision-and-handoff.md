# 07 修订与交付

把已通过质检的成品整理成可交付包，并把后续修订限定在「改一处、重渲一遍、留一条记录」的闭环里。本步不允许直接改 `deliver/` 里的成品；一切改动回到 `source/deck.json` 后再重新导出。

## 输入

| 输入项 | 来源 | 必需 |
|---|---|---|
| 通过的质检报告 | `<project>/records/qa-report.md`（结论为「通过」） | 是 |
| 工程源 | `<project>/source/deck.json` + `source/assets/` | 是 |
| 构建产物 | `<project>/build/deck.pptx`、`deck.pdf`、`preview/` | 是 |
| 修订请求 | 用户原话（含截图时记页码） | 视情况 |
| 用户原件 | 用户提供的源文件所在目录（只读） | 视情况 |

## 前置条件

- `records/qa-report.md` 结论为「通过（无 P0）」；不通过退回 `./06_quality-assurance.md` 6.6。
- 本次修订针对的 `source/deck.json` 有版本号（`meta.version`），无版本号先补 `1.0.0`。
- 用户原件已确认为只读；若尚未确认，退回 `./01_intake-and-content-audit.md` 步骤 1 补文件盘点表。

## 操作步骤

### 7.0 已批准清单与最小改动（防「改对了又被改坏」）

**规则：用户说「这个好 / 保留」就进清单**
- **触发条件**：用户对某页、某图、某句表示认可（「这个可以」「保持」「别动这页」）。
- **具体动作**：立刻写入 `records/approved.md`（一行：版本 / 页码 / 元素 name / 内容摘要 / 认可时间 / 原话）。后续修订不得改动清单内元素；确需改动，先说明理由并取得同意。
- **常见错误**：把针对封面的意见套到全册，顺手把用户满意的第 7 页配图也「优化」了，下一句就是「改回去」。

**规则：反馈三问，改前先说清**
- **触发条件**：收到含糊或有歧义的修改意见（「第一页的图换一下」「这页有点多余」）。
- **具体动作**：先答三问再动手：① 指哪一页（页码 + 元素）；② 只改哪一处（写出受影响的元素 name）；③ 其余页 diff 是否为空。歧义消不掉就给两个候选解释让用户一句话选，不要猜一种就改。
- **常见错误**：把「第一页图片不合适」理解成「所有页图片都要换」，一轮动 8 页，返工两小时。

**规则：最小改动，只动被指范围**
- **触发条件**：执行任何修订。
- **具体动作**：改完对比新旧 `deck.json`，列出改动页清单；未涉及的页必须逐字节相同。修订记录写「改动页：s01, s05；其余 9 页未变」。
- **常见错误**：为「顺手统一」把全册字号、边距一起调，连带把已通过 QA 的页面弄出新问题。

### 7.1 收修订请求并归类

| 类别 | 判定信号（用户怎么说） | 主改文件 | 影响面 |
|---|---|---|---|
| 内容 | 「这页说错了」「加一页竞品数据」「结论改成…」 | `records/project-brief.md` 定稿 → `source/deck.json` 文本 | 单页或相邻 2–3 页 |
| 视觉 | 「颜色太跳」「标题小一点」「这张图换掉」 | `source/deck.json` 的 `tokens` 或单元素样式 | `tokens` 类改全篇，元素类改单页 |
| 技术 | 「打不开」「字体变了」「导出 PDF 缺页」 | `source/deck.json` 非法字段 / 渲染后端 | 全篇构建 |
| 结构 | 「顺序倒过来」「删掉第二章」「加个目录页」 | `records/deck-outline.md` → `source/deck.json` 的 slides 顺序与 id | 全篇 id、页码、版式重复度 |

判据：一条请求只归 1 类；跨类拆成多条，先结构再内容再视觉。产出：修订清单（每条含类别、页码、原话摘录）。

### 7.2 定位受影响文件与页面

引用关系图（改上游必须先想下游）：

```
project-brief.md              事实与必须保留项
    │
design-proposal.md ─────► deck.json 的 tokens
deck-outline.md ────────► deck.json 的 slides 顺序/id/layout
slide-spec.md ──────────► deck.json 的 elements（坐标、字号）
                                  │
            build_pptx.py ────────┴──► build/deck.pptx
            render.py ────────────────► build/preview/slide-NN.png
            qa_check.py ──────────────► records/qa-report.md
```

定位三步：① 在 `source/deck.json` 里搜用户给的关键词，得到 `slide.id`；② 用该 id 在 `records/slide-spec.md` 找对应页规格；③ 判断改动落在 `tokens`（全篇）还是单个 `element`（单页）。判据：能说出「改哪个文件、哪一页、哪一种对象」三要素。产出：受影响文件清单 + 页码清单。

### 7.3 版本号与递增规则

- 格式 `MAJOR.MINOR.PATCH`，与 `meta.version`、交付文件名一致。
- MAJOR：结构变化（增删章节、页数变化 > 20%、换视觉系统）→ 例 `1.4.0 → 2.0.0`。
- MINOR：新增页或新增内容块、不改整体结构 → 例 `1.4.0 → 1.5.0`。
- PATCH：文案、坐标、字号、颜色微调 → 例 `1.4.0 → 1.4.1`。
- 每次交付必须递增且不同名，禁止 `final_v2_最终版` 这类命名。

### 7.4 执行修订并重跑链路

顺序固定：改记录文件（简报/规划表/规格）→ 改 `source/deck.json` → 构建 → 渲染 → 质检。命令同 05 与 06（`build_pptx.py` → `render.py` → `qa_check.py`）。判据：三个脚本退出码均为 0/1 合规，且 `build/preview/` 时间戳新于 `source/deck.json`。常见错误：只动 `build/deck.pptx`，下次构建被覆盖；只改文案不重渲，交付的 PDF 还是旧页。

### 7.5 交付目录结构

项目内保持四个目录，交付副本集中到 `deliver/`：

```
<project>/records/  project-brief / design-proposal / deck-outline / slide-spec / qa-report
<project>/source/   deck.json + assets/
<project>/build/    deck.pptx / deck.pdf / preview/ / contact-sheet.png / qa.json
<project>/deliver/  <项目名>_v<版本>.pptx / .pdf / preview/ / 交付说明.md
```

`deliver/` 只放交付副本与说明；交付说明写清工程路径，便于下一轮修订。

### 7.6 交付前 9 项核对

| 编号 | 核对项 | 合格判据 |
|---|---|---|
| 1 | 可打开 | PowerPoint 或渲染器能打开，页数与 `deck-outline.md` 一致 |
| 2 | 版本一致 | 文件名版本 = `meta.version` = 交付说明版本 |
| 3 | 质检通过 | `qa-report.md` 结论「通过」，P0 = 0 |
| 4 | 预览同步 | `deliver/preview/` 张数 = 页数，且由本次构建生成 |
| 5 | 无占位残留 | 全篇搜 `XXX`、`TBD`、`待补`、`lorem` 得 0 处，或已在遗留问题登记 <!-- allow-placeholder --> |
| 6 | 字体可显示 | `render-manifest.json` 的 `missingFonts` 为空，或已列入遗留问题 |
| 7 | 数字带单位 | 抽查 10 个数字，单位齐全率 100% |
| 8 | 原件未改 | 用户原件目录的文件数与修改时间未变 |
| 9 | 可复现 | `source/deck.json` + `source/assets/` 放在包内，他人可重建同版 |

### 7.7 不覆盖用户原件

- 只读挂载：把用户原件目录视为只读，任何解析、测量、截图都写到项目内副本。**触发条件**：需要改用户给的 PPT/Word/图片。**具体动作**：先 `cp` 到 `source/assets/` 再改副本。**常见错误**：直接存回用户原路径，覆盖其未备份版本。
- 交付另存：交付物写 `deliver/` 新文件，不覆盖用户同目录旧文件。
- **回滚准备**：每轮修订前把 `build/deck.pptx` 另存为 `deck_v<旧版本>.pptx`，至少留 2 版。

### 7.8 遗留问题记录格式

| 编号 | 类型 | 位置 | 现象 | 影响 | 计划 |
|---|---|---|---|---|---|
| L-01 | 视觉 | s07 第二组柱形 | 距安全边距 0.18 in，视觉偏挤 | 纯观感，不影响读取 | 下一版统一收紧 |
| L-02 | 内容 | s11 数据来源 | 缺第三方口径，仅内部统计 | 数值可读但不可对外引用 | 等用户提供口径 |

规则：编号连续；类型 ∈ {内容, 视觉, 技术, 结构}；位置精确到页与元素；影响写清「能否对外使用」；禁止写「后续优化」这类无计划项。

## 判断与分支

| 条件 | 动作 |
|---|---|
| 请求同时含结构和内容改动 | 先结构、后内容，分两轮交付，各升一次版本 |
| 修订涉及 `tokens` | 视为全篇改动，升 MINOR，全量重渲并重跑 6.1 |
| 修订只改 1–2 页文案 | 升 PATCH，可只渲指定页，但交付前必须全量重渲一次 |
| 质检出现新 P0 | 停止交付，回到 6.6 修复，版本再升 1 位 |
| 用户要求「直接改 pptx」 | 拒绝直接改成品；说明改动回到 `source/deck.json` 后再导出 |
| 页数变化 > 20% | 升 MAJOR，并在交付说明写明结构变化清单 |
| 用户原件在同一目录且同名 | 交付文件名加 `_v<版本>`，不覆盖；若必须同名则先备份原件 |

## 输出文件

- `<project>/deliver/<项目名>_v<版本>.pptx`
- `<project>/deliver/<项目名>_v<版本>.pdf`
- `<project>/deliver/preview/slide-NN.png`
- `<project>/deliver/交付说明.md`：版本、页数、字体、尺寸、工程路径、遗留问题表、修订清单。
- `<project>/records/qa-report.md`：追加本轮修订与复查记录，不删旧行。

## 完成标准

- 7.6 的 9 项核对全部为「是」，无一项「待确认」。
- 交付文件名包含版本号，且与 `meta.version` 逐字一致。
- 遗留问题 ≤ 5 条，每条有计划；影响对外使用的项必须为 0 条。
- `deliver/preview/` 张数 = 页数，全部由本轮构建生成。
- 用户原件目录的文件数与修改时间与交付前一致。
- `source/` 与 `records/` 未删，下一轮可从源头复现。

## 失败处理

| 类别 | 具体处理 |
|---|---|
| 缺素材 | 修订需替换的图/数据未到：该页保持上一版，登记遗留问题；交付说明标「等待素材，本版未改该页」 |
| 缺数据 | 数值待确认时不留空框，改用定性表述并登记；不得用占位数字交付 |
| 工具不可用 | 渲染或导出失败：先跑 `probe.py` 查后端，按 06 的失败处理切换 `--backend`；仍不可用则只交付 pptx + 源码，说明「PDF 未生成」 |
| 内容冲突 | 用户新要求与已确认事实冲突：以用户最新确认为准，在交付说明记录变更点与原依据，不静默改数 |

## 7.4 交付后：问一句要不要记住偏好（可选，默认不问也不记）

**触发条件**：用户对某一版明确表示满意（"就这样 / 可以了 / 不用再改"）。
**具体动作**：按 `references/preference-memory.md` §2 用三行交回合问一次；同意后把条目原文给他看，再 `python scripts/pref_memory.py --add entry.json --consented` 写入 `~/.design-memory/`；条目字段见 `templates/preference-entry.md`。
**常见错误**：把"机检 0 条"当满意；不问就写；写进项目目录（会跟着 git 提交）；记录客户名或项目数据。

- 结果三种：记（本轮写一条）/ 不记（什么都不写）/ 不回（默认不记）。
- 已有记录要用时，在阶段 0 说清"依据本地偏好记录，来源是 2026-11-15 那次"，并允许用户当场推翻。
- 记忆目录不在仓库内（脚本会拦 `.git` 路径）；放同步盘也算违规。
