# 能力状态：已实现 / 已验证 / 实验中 / 仅规划

> 依据：`docs/lighthouse-plan.md` 第 16 章第 5 问——「是否诚实地区分了已经实现、已经验证、正在实验和仅仅设想的能力」。
> 本文件是这五个问题的**唯一答案来源**。任何 README、宣传文案、交付说明里出现的"已支持"，都必须能在下表中找到对应状态与证据路径。

## 1. 四级定义与允许的表述

| 状态 | 判据 | 允许说 | 不允许说 |
|---|---|---|---|
| **已验证** | 有对照实验或负向测试，任何人按命令可复现同一结论 | "已验证（写明范围与条件）" | "保证 / 全面 / 任意场景" |
| **已实现** | 能跑、有产物、有命令，但没有对照实验 | "已跑通 / 已支持（写明边界）" | "已验证效果" |
| **实验中** | 有部分产物，未达该阶段验收标准 | "实验中 / 部分完成" | "已支持" |
| **仅规划** | 只有文档与设计，代码未写 | "规划中 / 未开工" | 任何现在时态的支持性描述 |

判定顺序：能复现的对照证据 > 负向测试 > 有产物 > 有文档。**低一级不得借用高一级的措辞。**

## 3. 使用规则（写文档、写宣传时逐条对照）

**触发条件**：写 README、CHANGELOG、release note、对外介绍、交付说明，或回答"支持什么"之前。

**具体动作**：
1. 先查第 2 节找到该能力的行，照抄它的状态词，不用近义词替换（"已跑通"不能写成"已支持"，"仅规划"不能写成"即将支持"）。
2. 写"支持 X"时，同一句里带上边界（例：仅 16:9 / 仅本机后端 / 只做受限改版）。
3. 新能力第一次进入仓库时，同步新增本表一行；没有证据路径的能力不许写进表。
4. 阶段门槛（G0–G4）未通过时，只能标"实验中"，不得标"已支持"。
5. 发现文档与表不一致：改文档，不改表（表是唯一真值）。

**常见错误**：
- 把"有产物"当成"已验证效果"——四套成片能跑通，不代表知识库被证明有效。
- 把"规划里写了"当成"即将支持"——规划书出现某个文件名，不等于仓库里有那个脚本。
- 用"全面 / 任意 / 保证"这类词替代边界条件。
- 只更新 README 不更新本表，导致两处口径分叉。

## 4. 本表的更新方式

- 每次发版前跑一次 `python scripts/stats.py --check`（规模数字）与 `python scripts/selfcheck.py --strict`（写作规范），再人工对一次本表。
- 状态从"仅规划"升为"已实现"必须有：脚本、命令、产物、失败处理四件东西同时存在。
- 状态从"已实现"升为"已验证"必须有对照或负向测试证据，并写清适用范围。
- 降级（例如发现某个"已验证"其实只跑过一次）要写进 CHANGELOG，不许静默。
