# 协作治理：谁能改什么，规划怎么不被改乱

本文是 [`CONTRIBUTING.md`](../CONTRIBUTING.md) 第 10 节的展开。它回答三个具体问题：开放写权限后**谁能改哪些文件**、**规划文件受什么保护**、**fork 与官方发布的边界在哪**。

一句话结论：**开放写权限 ≠ 开放规划解释权**。代码与知识库可以放开，规划（阶段顺序、版本序列、验收判据）要按契约管理。

---

## 1. 分级写权限

| 区域 | 谁能提 PR | 谁合并 | 合并前必须通过 |
|---|---|---|---|
| `scripts/`、`examples/` | 任何人 | 1 名维护者 | `selfcheck.py --strict` 0/0/0 + 改动脚本实跑一遍 |
| `discovery/`、`references/`、`workflows/`、`templates/` | 任何人 | 1 名维护者 | `selfcheck.py --strict` 0/0/0（三段式、检查清单不达标即退回） |
| `schema/`、`SKILL.md`、`CONTRIBUTING.md` | 任何人均可提 | 仅维护者 | `CHANGELOG.md` 记录 + demo 与三份案例机检回归到 0/0/0 |
| `docs/v2-plan.md`、`v2-plan-ops.md`、`v2-revision-notes.md` | 需先开提案 issue | 仅维护者 | 提案三问有答复（见第 2 节规则 2） |
| `dist/`、Release 附件、版本号 | 不提 PR | 仅维护者 | `stats.py --check` 0 + `selfcheck.py --strict` 0/0/0 + demo 的 `qa_check` 与 `copy_check` |

维护者也不能"自审自并"绕过最后一行：发布动作固定由三条闸门决定，闸门在脚本里，不在人脑里。

---

## 2. 规划文件的三条硬规则

**规则 1：阶段顺序与版本序列属于契约，不属于风格。**

**触发条件**：PR 想调整 P0–P4 的先后、删减阶段、改动"一阶段不过不进下一阶段"的门槛，或改动发布号序列。

**具体动作**：退回 PR，请对方开提案 issue 回答三问——①为什么现在改 ②不改会怎样 ③已有产物（案例、fixture、基线）如何迁移；维护者批准后走 `CHANGELOG.md` 的次版本号，并在 `v2-revision-notes.md` 记录理由与影响面。

**常见错误**：以"顺手优化结构"为由重排阶段，导致已完成阶段的验收判据失效、四套成片需要重跑。

**规则 2：规划改动只接受三类，不接受重写。**

**触发条件**：任何对 `docs/v2-plan*.md` 的修改。

**具体动作**：只受理——①与实现不一致的事实修正 ②缺口补充（新增判据、补失败处理）③验收判据的可执行化（把"检查一下"写成命令与期望输出）。重写文风、重命名阶段、扩大范围（例如"顺便支持网页长图"）一律不受理。

**常见错误**：把"重写一遍读起来更顺"当贡献，结果计划与 schema、脚本、验收判据脱节。

**规则 3：规划是公开的，改版权不是。**

**触发条件**：有人建议"别公开规划"或担心 fork 抢跑。

**具体动作**：说明规划本来就随仓库公开（MIT 许可，谁都能读、能 fork）；真正的风险不是被看到，而是被改乱与被冒名发布。因此：官方发布只认本仓库 Release 与 `install.md` 里的地址；fork 允许，但需标明"非官方派生"，不得声称维护者背书。

**常见错误**：为"防抄"把规划移出仓库或加密，使用者拿不到可执行计划，协作成本转嫁给了使用者。

---

## 3. 贡献者的三个不许

- **不许直接改发布物**：`dist/`、Release 附件、版本号，只由维护者在三条闸门通过后生成；
- **不许改已冻结基线**：`docs/v2-plan.md` 头部的基线数字、`CHANGELOG.md` 的历史条目、案例 README 的"源文件来源"——它们记录的是"当时真实跑过什么"，改了就等于伪造历史；
- **不许删署名与许可**：`LICENSE`、`NOTICE.md`、来源说明必须原样保留（MIT 本身要求保留版权与许可声明）。

---

## 4. 冒名与派生

项目名、仓库地址、`install.md` 里的安装地址是识别标志。派生版本要做三件事：

1. 改名或明确标注"非官方派生"；
2. 保留 `LICENSE`、`NOTICE.md` 与来源说明；
3. 不宣称与官方等价、不代替官方受理问题。

发现冒名发布（例如把派生版当官方版收付费），处理顺序：先在 issue 里联系 → 要求改名或加声明 → 仍不改则在 Release 说明中公开澄清边界。

---

## 5. 维护者同样受约束

维护者改规划也要开提案、写 CHANGELOG、跑三条闸门。"我能直接推"不是理由：跳过记录的改动，会让下一任维护者不知道某个阶段为什么被改。
