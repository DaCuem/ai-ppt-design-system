## ADR-003：发布号正常迭代（1.5.0 起），`v2` 只作功能线名称

- **日期**：2026-11-15
- **状态**：已接受
- **提出人**：项目发起人（口头纠正）+ 执行 AI 落盘
- **背景**：v2 R2 一度把"功能编号"（先做文档、后做 PDF）理解成"发布编号"，写出 `P2 → v1.2.0`、`P0/P1 → v2.0.0`、`P3 → v2.1.0` 的序列。这会造成后发布的版本号反而更小（v2.0.0 → v1.2.0），在 tag 与发布包里直接冲突。
- **目标**：服务 P7（可复现、可交接）；让版本号可被外部读者线性理解。
- **方案**：
  1. 发布号按正常迭代递增：`1.5.0（阶段 0）→ 1.6.0（文档骨架）→ 1.7.0（文档完整）→ 1.8.0（固定版面/PDF）→ 1.9.0（验收发布）`。
  2. `v2` 仅作为**功能线名称**（"文档与固定版面"这条线）出现在说明文字里，不进入版本号、tag 与文件名。
  3. 阶段顺序（0→1→2→3→4）本身保证"先做的功能编号小"，不需要在发布号上再做文章。
- **备选方案**：按功能线重编号（v1.2.0 / v2.0.0 / v2.1.0 混排）。未选，理由如上：会制造"后发版本号更小"的表面矛盾，且与 GitHub tag 习惯冲突。
- **影响**：`docs/v2-plan.md` §9.1 版本列、§12 整节、附录 D2；`docs/v2-plan-ops.md` §7 打包命令中的版本号；本文档第 1 章的序列。
- **风险**：读者看到标题里的 `v2` 会误以为版本号，已在 §12 与附录 A 术语里显式写明"v2 是功能线名称"。
- **验收**：`git tag` 序列单调递增；发布包文件名与 tag 一致；文档中不再出现 `v1.2.0` 作为未来版本。
- **回滚**：若将来真要并线（例如 3.0 大重构），按 ADR 重新定义版本方案，不就地改历史 tag。
- **证据**：`docs/v2-plan.md` §12；`docs/v2-revision-notes.md` §1.4。
