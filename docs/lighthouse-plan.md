## 0. 这份规划书的用途

这不是一份承诺"未来一定做完所有功能"的愿望清单，而是一份用于长期判断项目是否仍在正确方向上的**决策文件**。

无论项目推进到 v2、v3，还是几年以后重新审视，都应能通过本文回答：

1.  我们究竟想解决什么问题？
2.  当前正在做的功能，是否仍然服务于这个问题？
3.  设计知识库是否真的参与了 AI 的设计决策，还是只剩下文档和口号？
4.  新增一种文件或媒介时，是否复用了共同的设计能力，还是重新堆了一套互不相干的工具？
5.  项目是否在追求可验证的设计质量，还是只是在增加功能、文件数量和演示效果？

**使用规则：**
每次准备进入新阶段、增加新媒介、引入大型依赖、改变核心架构或发布重要版本前，先对照第
3、8、10 章。若核心目标不再成立，应先修正方向，而不是继续堆功能。

# 第一部分：方向基准

## 1. 项目最终要成为什么

### 1.1 一句话定义

**一个以设计知识库为核心，通过工作流指导 AI
做出设计决策，并借助不同媒介的专用工具链完成实现、检查、复核与交付的通用
AI 设计系统。**

PPT 是第一种被完整实现和验证的媒介，不是项目最终边界。

### 1.2 项目要解决的根本问题

当前 AI
已经能够生成文字、代码、图片、幻灯片和网页，但"能生成"不等于"能完成设计"。

常见问题包括：

-   没有充分理解任务，就急于生成结果；
-   把设计风格理解成配色、字体、装饰元素的表面组合；
-   只按单页或单个组件思考，忽略整体信息结构和视觉节奏；
-   反复使用模型熟悉的卡片、网格、渐变、图标堆叠等套路；
-   规则停留在自然语言描述，没有转化为具体动作；
-   产物无法稳定复现、检查、修改或交付；
-   机器检查通过后，就误以为设计质量已经得到保证。

项目的目标不是让 AI "多生成一点"，而是让 AI
在生成之前和生成过程中，能够**理解设计问题、调用相关知识、做出有理由的选择，并对结果进行检查和修正**。

### 1.3 目标用户获得的价值

用户不应只是得到一个文件，还应获得：

1.  **更合理的设计过程**：先理解需求和内容，再确定设计方向。
2.  **有依据的设计决策**：设计选择能够解释，而不是只给出"高级、简洁、有科技感"等形容词。
3.  **可复用的设计能力**：不同任务可以复用知识与方法，而不必从零开始写提示词。
4.  **可修改的成果**：尽量保留结构化源文件和可编辑产物。
5.  **可验证的质量**：明确哪些问题能由机器检查，哪些必须由人判断。
6.  **用户拥有最终决定权**：AI
    提供分析、方案和执行，用户确认方向与最终结果。

## 2. 不可改变的核心原则

以下原则是项目的长期约束。技术方案可以变化，原则不能被悄悄取消。

### P1｜设计知识必须参与决策

知识库不是项目装饰，也不是给 README 增加专业感的文章集合。

每一条重要知识都应能够影响至少一个具体环节，例如：

-   选择设计方向；
-   确定信息层级；
-   选择版式与构图；
-   制定颜色、字体、间距等视觉规则；
-   选择或处理图像；
-   识别并修正常见设计错误；
-   检查可读性、可访问性或媒介限制。

**判据：**
随机抽取一条知识规则，能够指出它在什么条件下被调用、改变了什么设计决策、产生了什么可观察结果，以及如何判断是否执行正确。若只能复述文章内容，不能指导动作，则这条知识尚未完成产品化。

### P2｜知识要可执行，而不只是正确

核心知识条目优先采用以下结构：

1.  **触发条件**：什么任务、内容关系或视觉问题下使用；
2.  **具体动作**：AI 应做什么，必要时给出数值、顺序、优先级或选择逻辑；
3.  **判断标准**：怎样知道执行结果符合要求；
4.  **常见错误**：容易出现什么偏差；
5.  **修正方式**：发现偏差后如何处理；
6.  **适用边界**：何时不适用，哪些情况需要人工决定；
7.  **来源或依据**：经验规则、设计理论、案例观察或测试结果。

不是每条知识都必须机械地填满所有字段，但核心执行规则必须能落到"触发---动作---判断"。

### P3｜设计不是固定皮肤

项目不能退化成一套固定模板、固定配色或固定风格。

-   风格是解决问题的方法，不是表面符号的复制。
-   颜色应由主题、品牌、内容和受众决定，不应把某种风格锁死为某组颜色。
-   版式应由信息关系决定，而不是每页从固定模板菜单中随机抽取。
-   同一设计原则在不同媒介中可以有不同实现。

**判据：**
同一工作流处理不同主题时，应能形成有实质差异、且与任务匹配的视觉结果，而不是只替换标题和色值。

### P4｜完整流程优先于单点生成

长期保留完整链路：

`理解需求 → 内容分析 → 形成方案 → 设计系统 → 结构规划 → 制作实现 → 质量检查 → 人工复核 → 迭代交付`

新媒介可以调整阶段名称和局部步骤，但不能因为某个生成器容易实现，就把项目缩减成"一句话生成文件"。

### P5｜机器检查与人的设计判断分工

-   机器负责可明确计算、可重复验证的事实性问题。
-   AI 可以辅助视觉审查、提出修改建议，但不能把自我评价当作独立验收。
-   人负责审美判断、任务适配、内容取舍和最终验收。

**底线：** `QA 全通过` 不等于"设计优秀"。任何宣传和文档都不得混淆二者。

### P6｜用户拥有最终决定权

AI
可以追问、比较、提出建议、指出风险，但不能擅自替用户确定未确认的内容。

-   需求不明确时标注假设；
-   设计方向应提供可比较的选项；
-   重要偏好记忆必须经用户同意；
-   交付时明确说明已确认项、假设项和未解决问题。

### P7｜可复现、可维护、可交接

关键产物应尽可能具有明确的数据结构、输入输出契约、版本记录和验证方法。不能只依赖某一次对话中的隐含上下文。

## 3. 跑偏判据：哪些变化可以接受，哪些不可以

### 3.1 可以变化的内容

以下内容可以随着技术、用户反馈和媒介变化而调整：

-   具体使用哪一种模型；
-   使用 Markdown、JSON、数据库或其他知识存储方式；
-   使用 Python、JavaScript、浏览器工具或其他实现技术；
-   工作流的阶段名称、执行顺序和交互方式；
-   具体的渲染器、导出工具和检查工具；
-   视觉风格库的分类方式；
-   先支持哪一种新媒介；
-   哪些检查由脚本完成，哪些由模型或人完成。

调整这些内容时，必须说明它们如何更好地服务核心目标。

### 3.2 不可以悄悄变化的内容

以下变化需要重新进行项目级决策，不能作为普通功能更新混入：

-   从"指导 AI 做设计"变成"批量生成文件"；
-   从设计知识库驱动，退化成大量提示词和模板拼接；
-   从完整设计流程，退化成单一生成器或自动质检器；
-   把固定风格包装成通用设计能力；
-   只追求文件数量、代码行数、支持格式数量或演示效果；
-   为了快速支持新媒介，放弃可复现、可编辑和质量验证；
-   把未验证的能力写成已经实现；
-   把用户的最终决定权交给模型。

### 3.3 红色警报

出现以下任一情况，暂停扩展功能，先做方向复核：

1.  新增功能无法说明它服务于哪条核心原则。
2.  新媒介有生成器，却没有需求理解、设计决策或质量复核流程。
3.  设计知识库的条目越来越多，但工作流没有实际调用它们。
4.  设计结果越来越像同一套模板，主题差异只体现在颜色和标题。
5.  项目宣传的能力超过仓库中可复现的实现。
6.  机器 QA 被当成唯一质量标准。
7.  只有作者本人能解释如何运行、如何验收和如何修改。
8.  新增一个媒介就复制一整套知识体系，导致不同媒介的设计原则互相矛盾且无法共享。

# 第二部分：目标架构

## 4. 长期架构：一个设计核心，多种媒介适配器

项目未来不应简单变成"PPT Skill + Word Skill + 网页 Skill + 图片
Skill"的松散集合。

建议采用分层架构：

``` text
用户任务
   │
   ▼
任务理解与需求探索
   │
   ▼
共享设计核心（Design Core）
   ├── 设计原则
   ├── 视觉风格与设计方法
   ├── 信息架构与叙事
   ├── 排版、色彩、图像、图表
   ├── 反模式与修正策略
   ├── 可访问性与可读性
   └── 用户偏好与项目约束
   │
   ▼
媒介适配层（Medium Adapters）
   ├── Slides：页面画布、页间节奏、演示可读性
   ├── Documents：流式排版、章节结构、页眉页脚、打印规范
   ├── Fixed Layout：海报、画册、单页、固定画布
   └── Web：DOM、CSS、响应式布局、交互与状态
   │
   ▼
媒介专属实现工具链
   ├── Schema / Source
   ├── Builder / Renderer
   ├── Automated QA
   └── Preview / Export
   │
   ▼
人工复核与迭代交付
```

### 4.1 共享设计核心负责什么

共享核心只存放跨媒介仍然成立的设计知识，例如：

-   视觉层级；
-   对齐、间距、邻近与分组；
-   对比、重复、统一与平衡；
-   色彩关系与色彩角色；
-   字体与文字层级；
-   图像选择、裁切和视觉权重；
-   信息架构、阅读路径与叙事节奏；
-   设计风格的形成方法；
-   常见 AI 设计反模式；
-   可访问性与可读性原则；
-   用户偏好和项目品牌约束。

共享核心不应把某一种媒介的实现细节伪装成通用原则。例如，"页面元素使用绝对坐标"是特定画布模型的实现方式，不是所有设计媒介的共同规则。

### 4.2 媒介适配层负责什么

每种媒介必须有自己的规则和技术契约。

  ---------------------------------------------------------------------------------------------------------------------------------
  媒介                    特有设计问题                                           必须具备的实现与检查能力
  ----------------------- ------------------------------------------------------ --------------------------------------------------
  PPT / Slides            页面叙事、演示距离、页间节奏、单页信息密度             页面 Schema、PPTX 构建、渲染、版面 QA、整套总览

  Word / Documents        连续阅读、章节层级、段落流动、分页、打印               文档 Schema、DOCX 构建、PDF 导出、分页与样式 QA

  PDF / Fixed Layout      固定尺寸、出血、安全边距、图文定位、既有文件改版边界   页面模型、PDF/PNG/SVG 导出、逐页 QA、前后对照

  Web                     流式布局、响应式断点、交互状态、语义结构、可访问性     HTML/CSS/JS
                                                                                 或组件输出、断点测试、浏览器渲染、交互与可访问性
                                                                                 QA
  ---------------------------------------------------------------------------------------------------------------------------------

**重要：**
不同媒介共享设计知识，不代表可以共用同一套布局模型和渲染脚本。共享的是设计决策依据；适配的是媒介表达与工程实现。

### 4.3 知识库如何真正"干预"AI

长期应把"调用知识库"设计成可追踪的决策过程：

1.  任务分析识别当前设计问题；
2.  路由器根据任务、媒介和内容关系检索相关知识；
3.  AI 读取规则并形成设计决策；
4.  决策记录引用使用的知识条目及理由；
5.  媒介适配器把决策转为具体结构和参数；
6.  检查器验证可计算的约束；
7.  视觉复核判断规则是否被正确表达；
8.  发现问题后回写案例或修正规则。

建议为每个重要设计决策保留轻量记录：

``` json
{
  "decision": "采用左右对照结构呈现两种方案",
  "problem": "用户需要比较两种方案的差异",
  "knowledge_refs": [
    "design-principles/proximity",
    "layout-recipes/comparison"
  ],
  "reason": "让相同维度在相同位置对齐，降低横向比较成本",
  "medium": "slides",
  "verification": "检查两列维度一致，并进行缩略图可读性复核"
}
```

该结构只是建议的数据示例，不要求所有普通操作都生成冗长日志。优先记录关键决策，避免让追踪机制本身成为负担。

# 第三部分：可执行路线图

## 5. 阶段安排与进入条件

路线图按能力成熟度推进，不按日历强行赶工。阶段可以并行准备，但没有达到前一阶段的门槛，不应把下一阶段宣传为正式能力。

### 阶段 0｜巩固 PPT 基线与验证设计知识的作用

**定位：** 不是继续堆 PPT
功能，而是证明当前核心流程稳定、知识库确实参与了设计。

**执行任务**

-   [ ] 固定一个可复现的 PPT
    基准任务，保留完整需求、内容、约束和输入素材。
-   [ ] 选择至少三个明显不同的任务类型（例如学术、工程、创意）。
-   [ ]
    为每个任务保存需求记录、关键设计决策、知识条目引用、`deck.json`、PPTX、渲染图和
    QA 报告。
-   [ ]
    对知识库做消融对照：同一模型、同一任务、相同工具条件下，对比"正常调用知识库"和"不给设计知识库"的结果。
-   [ ] 由不知道实验组别的评审者进行盲评。
-   [ ]
    记录模型版本、提示词、运行日期和人工修改量，避免把模型更新误认为知识库效果。
-   [ ] 检查不同主题是否产生真正不同的设计方案，而不是只换色。

**交付物**

-   `docs/evaluation/baseline-tasks.md`
-   `docs/evaluation/ablation-protocol.md`
-   `docs/evaluation/results/`
-   至少三套可复现基准案例
-   更新后的验证报告

**验收标准**

-   所有案例可以从源文件重新构建和渲染。
-   机器检查能稳定复现，负向样例能被正确拦截。
-   盲评至少覆盖任务适配、信息层级、构图差异、视觉一致性、可读性五个维度。
-   报告必须呈现正面结果和失败案例，不得只挑选好看的页面。
-   如果知识库组没有稳定优于对照组，不能宣称"知识库已经被证明能提升设计质量"；应定位问题发生在哪个环节（检索、规则质量、模型遵循、工具实现或评估方法）。

**阶段门槛 G0**

只有当 PPT
工作流可复现、基准任务固定、评估方法透明，才进入新媒介的正式扩展。若消融实验暂时无法得出结论，可以继续完善
PPT，但必须保留"效果尚未充分证明"的状态。

### 阶段 1｜Word / 文档分支

**定位：** 验证共享设计核心能否迁移到连续阅读型文档，而不是把 PPT
页面硬塞进 Word。

**依据现有规划：** v2 R2 已提出 `doc.json → DOCX → PDF`
的文档分支；正式开工前仍应按仓库决策流程确认范围和验收条件。

**执行任务**

-   [ ]
    确认文档类型边界：先支持报告、说明文档、提案等常见文档，不承诺所有复杂
    Word 域功能。
-   [ ] 定义 `doc.json`
    Schema，明确段落、标题、列表、表格、图片等块模型。
-   [ ] 定义文档
    preset：页面尺寸、页边距、字体、字号档、行距、段落间距和内容密度。
-   [ ] 实现 `doc.json → .docx` 的可编辑构建链。
-   [ ] 实现 PDF 导出与逐页预览。
-   [ ] 建立 Schema QA、DOCX QA、PDF/Render QA 三层检查。
-   [ ]
    将共享设计知识转换为文档场景规则，例如章节层级、段落长度、表格可读性和分页控制。
-   [ ] 用至少三种不同结构的文档案例验证，而不是只用一种报告模板。

**交付物**

-   `schema/doc.schema.json`
-   `scripts/build_docx.py`
-   `scripts/export_pdf.py`
-   `scripts/qa_doc.py`
-   `workflows/document/`
-   `examples/documents/`
-   文档分支验证报告

**验收标准**

-   源文件可重复构建为可编辑 DOCX。
-   PDF 导出后分页、字体、表格和图片位置经过检查。
-   修改内容后能重新生成，不需要手工修补大量页面。
-   不同文档结构可以共享设计核心，但不能全部呈现为同一版式。
-   明确列出暂不支持的复杂域、自动编号或特殊排版能力。

**阶段门槛 G1**

只有当文档从需求到交付形成完整闭环，并有多种案例证明不是单模板系统，才把"文档设计"列为正式支持媒介。

### 阶段 2｜PDF 与固定版面设计

**定位：**
面向页面尺寸固定、视觉构图优先的设计任务，例如海报、单页、画册页面和信息图。

**执行任务**

-   [ ] 明确固定版面与连续文档的边界：固定画布不使用文档流式排版模型。
-   [ ] 定义页面尺寸、出血、安全区、网格和导出分辨率规则。
-   [ ] 建立固定版面 Schema，优先复用已验证的结构化元素模型。
-   [ ] 实现可复现的 PNG / SVG 导出。
-   [ ] 评估分层 PNG 与坐标清单是否能满足后续编辑需求。
-   [ ] 为 PDF
    既有文件改版设定明确边界：保留底图、简单背景遮挡、局部覆盖和前后对照；不能承诺任意
    PDF 无损编辑。
-   [ ] 对复杂背景、不可恢复内容和不可编辑文字主动报告限制。
-   [ ] 建立固定版面案例和像素级/几何级检查。

**交付物**

-   `schema/page.schema.json`
-   `workflows/fixed-layout/`
-   `scripts/export_svg.py`
-   `scripts/export_layers.py`（若验证后保留）
-   `examples/fixed-layout/`
-   PDF 改版边界说明与验证报告

**验收标准**

-   输出尺寸、分辨率和安全区可以检查。
-   SVG 仅对明确支持的元素承诺矢量导出。
-   分层文件可以按坐标清单重新组合，且图层关系可解释。
-   PDF 改版提供 before/after 对照和逐项变更记录。
-   不把"可导出 SVG / PNG"宣传成"支持 PSD 原生工程文件"。

**阶段门槛 G2**

只有当固定版面具备独立的模型、工具链和质量检查，不再依赖 PPT
页面模型勉强适配，才正式纳入支持范围。

### 阶段 3｜网页设计与实现

**定位：** 从静态画布走向具有流式布局、响应式行为和交互状态的网页。

**当前状态：** 网页/H5 不属于现有 v2 R2
的正式范围。当前固定画布与绝对坐标模型不能直接承担响应式网页设计。网页应作为独立媒介分支研究，不能提前宣传为已支持。

**执行任务**

-   [ ]
    先定义网页任务边界：落地页、作品集、产品介绍页或仪表盘，选一个作为首个试点，不一开始承诺全站系统。
-   [ ] 研究并定义网页专用结构模型：语义结构、组件树、布局约束、设计
    tokens、交互状态。
-   [ ] 将共享知识映射到 CSS
    Grid、Flexbox、排版尺度、组件层级、响应式断点等网页概念。
-   [ ] 建立断点策略，至少覆盖窄屏、常规桌面和宽屏。
-   [ ] 建立浏览器渲染与截图对比流程。
-   [ ] 检查键盘操作、语义结构、颜色对比度、焦点状态和基本可访问性。
-   [ ] 对交互行为建立明确状态与验收步骤，不能只凭静态截图判断完成。
-   [ ] 用真实浏览器验证不同视口，不以单张桌面截图作为响应式验收。
-   [ ] 进行网页分支消融实验，验证共享设计知识是否真正影响网页结果。

**交付物**

-   `schema/web.schema.json` 或等价组件/页面契约
-   `workflows/web/`
-   `adapters/web/`
-   `scripts/` 中的浏览器渲染与 QA 工具
-   至少一个可部署的网页案例
-   多视口与交互测试报告

**验收标准**

-   同一页面在规定视口下均能合理布局，不出现依赖绝对坐标的整体失效。
-   页面具备真实 DOM 结构和可操作交互，而非仅导出一张图片。
-   关键组件具有明确状态、语义和可访问性检查。
-   网页案例能从源文件或项目配置重新构建。
-   共享设计知识与网页专属规则边界清楚。
-   有对照实验或可审查案例说明知识库如何影响网页设计决策。

**阶段门槛 G3**

在达到上述标准之前，网页只能标注为研究中或实验性，不得列为稳定支持媒介。

### 阶段 4｜统一任务入口与跨媒介协作

**定位：** 当多个媒介分支分别成熟后，再统一任务入口和交付体验。

**执行任务**

-   [ ] 让用户先描述设计目标，再由系统判断适合哪种媒介。
-   [ ] 支持同一项目在不同媒介间共享品牌、受众、内容和偏好。
-   [ ] 明确区分共享偏好与媒介专属偏好。
-   [ ]
    支持从一个媒介派生另一个媒介，但必须重新检查媒介约束，不能简单缩放或复制。
-   [ ] 统一交付说明、质量报告、版本记录和用户确认机制。
-   [ ] 评估是否需要统一的设计决策记录和知识引用格式。

**交付物**

-   统一任务入口
-   跨媒介项目上下文规范
-   共享偏好与媒介偏好规范
-   跨媒介案例
-   统一质量报告格式

**验收标准**

-   用户无需重复提供已确认且适用于多个媒介的信息。
-   媒介专属约束不会被错误共享。
-   跨媒介派生后，仍分别通过对应媒介的 QA。
-   统一入口不会为了"看起来统一"而隐藏媒介差异。

**阶段门槛 G4**

至少两个不同媒介分支独立达到稳定标准，且跨媒介共享确实减少重复工作、没有降低质量，才进入统一入口阶段。

## 6. 每个新媒介立项前必须回答的问题

未来任何人提出"我们也支持 X 格式吧"，都必须先写一页媒介立项说明。

  ----------------------------------------------------------------------------------------
  必答问题                            必须给出的答案
  ----------------------------------- ----------------------------------------------------
  用户任务是什么？                    明确用户要完成的实际设计任务，而不是只列文件扩展名

  该媒介的独特设计问题是什么？        例如响应式、分页、演示距离、出血或交互状态

  哪些知识可以复用？                  指出共享知识条目，不要笼统写"复用设计知识库"

  哪些知识必须新增？                  明确媒介专属规则

  源文件是什么？                      给出 Schema、组件模型或其他结构化契约

  如何生成？                          指定 builder / renderer 和输入输出

  如何检查？                          列出机器可检查项与人工复核项

  如何证明有效？                      给出基准任务、对照方案和评价方式

  不支持什么？                        写出明确的能力边界与降级策略

  什么时候算完成？                    写出可复现的验收标准和样例
  ----------------------------------------------------------------------------------------

**否决条件：**
如果一个媒介只有"能导出文件"的实现，却没有设计决策流程和质量闭环，不得将其作为完整媒介发布。

# 第四部分：知识库治理与质量验证

## 7. 设计知识库的长期维护制度

### 7.1 知识条目的生命周期

``` text
问题 / 观察 / 设计理论 / 用户反馈
              │
              ▼
          提出知识条目
              │
              ▼
       明确触发条件与动作
              │
              ▼
       绑定案例或可检查结果
              │
              ▼
       在真实任务中试用
              │
       ┌──────┴──────┐
       ▼             ▼
     有效           无效/冲突
       │             │
       ▼             ▼
   正式纳入       修改/废弃/限定范围
       │
       ▼
  更新版本与验证记录
```

### 7.2 知识库准入标准

新增知识条目至少满足以下条件：

-   [ ] 解决了明确的设计问题。
-   [ ] 有适用条件，不是无条件命令。
-   [ ] 能指导 AI 做出具体动作。
-   [ ] 有判断执行结果的标准，或明确说明为何只能人工判断。
-   [ ] 不与已有权威规则重复或冲突。
-   [ ] 有案例、依据或验证计划。
-   [ ] 对不适用的情况给出边界。

### 7.3 知识库不能无限膨胀

新增内容前先检查：

1.  是否已有相同规则？
2.  是否应该修订旧规则，而不是再新增一条？
3.  这条知识是否真的会被工作流调用？
4.  是否会增加检索噪声或互相冲突？
5.  能否通过一个小案例验证它的价值？

如果只是有趣的设计知识、但短期内不能进入工作流，可以放入阅读资料或研究区，不要直接提升为执行规则。

### 7.4 反模式库必须持续针对真实失败

反模式不应只收集"看起来不高级"的设计现象。每条反模式都应记录：

-   可观察症状；
-   模型为什么容易这样做；
-   哪些条件下构成问题；
-   如何检测；
-   如何修正；
-   哪些情况下它其实是合理选择。

尤其关注模型常见捷径：卡片堆叠、强行三栏/四栏、无意义图标、装饰性渐变、标题与正文层级失衡、所有页面结构雷同等。

## 8. 证明知识库有效：评估制度

项目的核心差异是"设计知识库参与 AI
设计决策"，因此必须建立证据，而不能只靠作者主观感受。

### 8.1 基础消融实验

对同一任务运行两个条件：

-   **A 组：**
    使用相同模型、相同基础任务要求和相同工具，但不提供项目设计知识库。
-   **B 组：**
    使用相同模型、相同任务要求和工具，并按项目工作流调用设计知识库。

必须尽可能控制模型版本、生成参数、输入内容、工具权限和运行环境。若无法控制，应在报告中明确记录差异。

### 8.2 评价维度

建议采用 1--5 分量表，并要求评审者写出具体证据。

  维度         评审问题
  ------------ --------------------------------------------
  任务适配     设计是否真正回应受众、场景和目标？
  信息层级     重点是否清晰，阅读路径是否合理？
  构图与版式   布局是否服务于信息关系，而非套用套路？
  视觉一致性   规则是否一致，又是否避免机械重复？
  主题差异     不同任务是否形成有实质差异的视觉表达？
  可读性       文字、图表、对比度和信息密度是否适当？
  反模式控制   是否减少无意义卡片、装饰、图标堆叠等问题？
  修改成本     达到可交付质量需要多少轮人工修改？

评审者应尽量不知道作品来自 A 组还是 B
组。不能只比较"哪一份更漂亮"，还要比较任务适配与修改成本。

### 8.3 实验报告必须包含

-   任务原文和输入材料；
-   模型与工具版本；
-   A/B 两组完整设置；
-   两组原始产物；
-   评审者数量与评分；
-   评分分布和评语；
-   人工修改轮数或修改时间；
-   失败案例；
-   结论适用范围；
-   尚不能证明的内容。

### 8.4 结论分级

  ------------------------------------------------------------------------------------
  证据情况                            允许使用的表述
  ----------------------------------- ------------------------------------------------
  只有规则文档和工作流引用            "设计知识已接入工作流"

  有案例展示规则被执行                "已在这些案例中验证规则执行"

  有受控对照，结果稳定改善            "在指定任务与模型条件下，知识库带来可观察改善"

  多模型、多任务、多媒介重复验证      才能讨论更广泛的通用效果
  ------------------------------------------------------------------------------------

**禁止越级宣传。** 在证据不足时，不能说"显著提升所有 AI
的审美""保证生成专业设计"等。

# 第五部分：项目管理与发布

## 9. 每次迭代的标准工作方式

### 9.1 开始前

-   [ ] 写清楚本次要解决的用户问题。
-   [ ] 指出对应的核心原则。
-   [ ] 判断这是修复、知识库改进、媒介适配还是新功能。
-   [ ] 查阅现有架构和相关知识，避免重复造轮子。
-   [ ] 明确输入、输出、失败边界和验收标准。
-   [ ] 评估是否会影响已有媒介和案例。

### 9.2 实现中

-   [ ] 优先小步修改，避免一次性重写多个层次。
-   [ ] 结构、知识、工作流和工具职责分开。
-   [ ] 所有阈值尽量只有一个权威定义，其他文件引用它。
-   [ ] 新规则要有对应案例或测试。
-   [ ] 不确定的内容标注假设，不包装成事实。
-   [ ] 不为追求抽象架构而提前建设没有实际用例的复杂系统。

### 9.3 发布前

-   [ ] 运行完整自检与已有测试。
-   [ ] 重新构建代表性案例。
-   [ ] 渲染并人工查看整体结果。
-   [ ] 检查负向测试是否仍能发现问题。
-   [ ] 更新 README、版本说明、项目总结和能力边界。
-   [ ] 确认宣传内容与仓库真实能力一致。
-   [ ] 记录已知问题和下一阶段门槛。

### 9.4 每个版本必须留下的证据

  证据       作用
  ---------- ------------------------
  变更记录   说明为什么改、改了什么
  测试记录   说明功能是否按预期工作
  案例产物   说明实际效果
  渲染预览   允许人检查视觉结果
  QA 报告    说明机器发现了什么
  能力边界   说明目前不能做什么
  回归结果   说明旧能力是否被破坏

## 10. 长期方向审查表

每次大版本发布前，逐项回答。不能只打勾，必须给出仓库证据或案例链接。

  -----------------------------------------------------------------------------------------
  审查问题                       通过标准                           不通过意味着什么
  ------------------------------ ---------------------------------- -----------------------
  项目是否仍在解决"让 AI         README、主 Skill 和真实工作流一致  定位漂移
  按设计方法工作"？                                                 

  设计知识是否被实际调用？       有任务路由、知识引用或可追踪决策   知识库沦为资料库

  规则是否能转化为动作？         有触发条件、动作、判断标准         规则空泛

  是否避免固定模板化？           多主题案例存在实质差异             退化为模板生成器

  是否保留完整设计流程？         从需求到交付有明确阶段与门禁       退化为单点生成器

  是否有可复现产物？             源文件、构建命令、渲染结果齐全     只能演示，不能交付

  是否区分机器检查和审美判断？   QA 报告与人工复核均存在            质量标准失真

  新媒介是否有独立适配？         专属 Schema、渲染与 QA             生硬移植

  是否有真实证据支持宣传？       版本、案例、测试和文案对应         过度承诺

  用户是否保留决定权？           关键方向和偏好由用户确认           自动化越权
  -----------------------------------------------------------------------------------------

**判定规则：**

-   核心前五项任意两项不通过：暂停新功能，优先修复方向。
-   "知识库是否实际调用"或"是否保留完整设计流程"任意一项不通过：不得发布为新的完整媒介能力。
-   "宣传是否有证据"不通过：先修正宣传与文档，再发布。
-   新媒介专属架构或 QA 不通过：只能标记实验性，不得标记稳定支持。
-   所有项通过，也不意味着项目已经优秀，只说明它仍在沿着正确目标推进。

# 第六部分：边界、风险与决策机制

## 11. 明确不追求的东西

为了保持项目聚焦，以下内容不应成为项目的主要目标：

-   不追求支持尽可能多的文件扩展名；
-   不追求把所有设计工作都压缩成一个万能提示词；
-   不追求做成只会套用固定模板的生成器；
-   不追求让机器对所有审美问题给出绝对结论；
-   不追求在每个媒介上都自己实现完整编辑软件；
-   不追求为了宣传而提前宣布未完成的能力；
-   不追求与所有现有 Skill 进行无意义的全面排名；
-   不追求把知识库做成越大越好的百科全书。

可以借鉴其他项目的优秀方法，但必须回答：它解决了什么问题？是否适合本项目？会不会破坏现有原则？是否值得增加维护成本？

## 12. 风险清单

  --------------------------------------------------------------------------------------------------
  风险                     早期信号                           应对方式
  ------------------------ ---------------------------------- --------------------------------------
  知识库文档化、执行弱化   文件越来越多，决策中看不到引用     增加路由与决策记录，删除无效条目

  过度工程化               抽象层很多，真实案例很少           回到一个具体任务验证

  媒介扩张过快             多种格式都能导出，但没有质量闭环   暂停扩张，先完成一个媒介分支

  依赖模型"自觉遵守"       同一规则执行结果波动大             关键约束结构化、工具化；保留人工检查

  机器 QA 越界             把可计算指标当成审美评分           明确机器与人的责任边界

  案例偏置                 只展示最成功的页面                 保留失败样例与修正记录

  模型升级造成回归         新模型改变风格或忽略规则           固定基准任务，版本升级后回归测试

  用户偏好污染任务         旧偏好不适合新项目                 偏好按媒介/项目隔离，并允许临时覆盖

  项目定位被宣传稀释       外部只记住"PPT 自动检查"           统一一句话定位和八阶段流程表达

## 13. 决策记录模板

每次改变核心架构、支持媒介范围或知识库治理规则时，新增一条决策记录：

``` markdown
## ADR-XXX：决策标题

- 日期：
- 状态：提议 / 已接受 / 已废弃
- 背景：当前遇到什么问题？
- 目标：本次决策服务于哪条核心原则？
- 方案：具体准备怎么做？
- 备选方案：考虑过什么？为什么不选？
- 影响：会影响哪些媒介、知识、工具和用户体验？
- 风险：可能引入什么问题？
- 验收：如何判断决策有效？
- 回滚：如果失败，如何恢复？
- 证据：相关案例、测试或讨论链接
```

## 16. 每次回看项目时，只问这五个问题

如果几年后只剩下时间读五个问题，就读下面这五个：

1.  **我们是否仍在让 AI 按设计方法工作，而不只是让它生成文件？**
2.  **设计知识是否真的改变了 AI 的决策，还是只存在于仓库文档里？**
3.  **同一套核心知识能否在不同主题、不同媒介中被正确转化，而不是复制固定模板？**
4.  **每一种对外宣称支持的媒介，是否都有完整、可复现、可检查的交付闭环？**
5.  **我们是否诚实地区分了已经实现、已经验证、正在实验和仅仅设想的能力？**

只要这五个问题始终能得到有证据的肯定回答，项目就没有忘记自己的目标。
