# 消融实验协议：知识库到底有没有改变 AI 的设计

> 依据：`docs/lighthouse-plan.md` §8「证明知识库有效：评估制度」。
> 当前状态：**未开始**。本文件是"怎么做"，不是"做过了"。任何"知识库提升了设计质量"的说法，在本协议跑完并写进 `docs/evaluation/results/` 之前都不得使用。

## 1. 要回答的问题

一句话：**同一模型、同一任务、同一工具下，读了本项目设计知识库的那一组，产出是否比没读的一组更好？**

更精确的三个子问题：
1. 它是否改变了设计决策（结构、层级、版式选择），而不只是措辞？
2. 改动是否稳定（同任务重复跑仍然更好，而不是有一次撞对）？
3. 改善是否与"知识库"这一变量相关，而不是模型版本、提示词写法或人工修改量的差异？

## 2. 两组的唯一差别

| 项 | A 组（对照） | B 组（实验） |
|---|---|---|
| 模型与参数 | 同一模型、同版本、同温度 | 同 A |
| 任务原文 | 同一份，逐字相同 | 同 A |
| 工具链 | 同版本脚本，同命令 | 同 A |
| 时间预算 | 相同上限 | 同 A |
| **知识库** | **不提供**：不读 `references/`、不读 `SKILL.md` 的规则表、不给知识条目引用 | **按工作流调用**：走 `SKILL.md` 路由，产出 `knowledge_refs` |
| 人工干预 | 只允许修环境错误，不允许调版面 | 同 A |

**A 组的操作要点**（最容易做错）：不是"把规则删掉"，而是**开一个不加载本仓库知识的干净会话**，只给它任务原文与工具说明。若做不到干净会话，就在提示里明确"禁止读取 `references/` 与 `SKILL.md`"，并在报告里披露这条限制——否则 A 组会被污染，实验作废。

## 3. 执行步骤（S1–S9）

| 步骤 | 动作 | 产出 |
|---|---|---|
| S1 | 冻结基线：`git tag` 记录仓库版本，确认三份基准任务的 `qa.json` 全 0 | `run.json` 头部字段 |
| S2 | 建结果目录：`docs/evaluation/results/<日期>-<任务号>-R<版本>/`（含 `A/`、`B/`） | 目录 |
| S3 | 跑 A 组：干净会话 + 任务原文 + 工具说明，产出 deck.json 与 pptx | `A/` 全套产物 |
| S4 | 跑 B 组：同一会话条件，按 `SKILL.md` 走流程，记录 `knowledge_refs` | `B/` 全套产物 |
| S5 | 对两组各自跑第 4 节的验收命令，记录 `qa_summary` / `copy_summary` | `A/qa.json`、`B/qa.json` |
| S6 | 生成匿名对照：把两组的 contact-sheet 重命名为 `P01`/`P02`（随机顺序，映射表另存） | `anon/` |
| S7 | 盲评：至少 3 名评审（或 1 名评审 + 两轮间隔 24 h，须披露） | 评分表 |
| S8 | 统计与结论：按第 6 节分级写结论，不许越级 | `report.md` |
| S9 | 回写：把失败案例加入 `references/anti-patterns.md` 候选，把有效规则补上 `knowledge ref` | 变更记录 |

重复次数：每份任务至少 **2 次独立运行**（共 3 任务 × 2 组 × 2 次 = 12 次产出），用于看稳定性。条件不允许时降到 1 次，但必须写明"单次运行，无法判断稳定性"。

## 4. 两组都要过的机器验收

```powershell
& $PY scripts\qa_check.py  --deck "<组>\source\deck.json" --out "<组>\build\qa.md"  --json "<组>\build\qa.json"
& $PY scripts\copy_check.py --deck "<组>\source\deck.json" --out "<组>\build\copy.md" --json "<组>\build\copy.json"
```

记录：`qa_summary` 四项、`copy_summary` 的 P0/P1 计数、页数、元素总数、文本块总数、平均留白率。

**注意**：机器指标只进"过程数据"表，**不能**直接当"设计更好"的证据。A 组可能因为页数少而"更干净"，B 组可能因为信息更全而元素更多——两者都不是优劣判断。

## 5. 盲评：8 个维度，1–5 分，必须写证据

| 维度 | 评审问题 | 1 分 | 5 分 |
|---|---|---|---|
| 任务适配 | 是否真正回应受众、场景和目标 | 明显偏题 | 每页都在服务目标 |
| 信息层级 | 重点是否清晰、阅读路径是否合理 | 找不到重点 | 一眼看到结论与依据 |
| 构图与版式 | 布局是否服务信息关系，而非套套路 | 明显模板感 | 结构由内容决定 |
| 视觉一致性 | 规则是否一致，又不机械重复 | 每页各自为政 | 一致且有节奏变化 |
| 主题差异 | 不同任务是否形成实质差异 | 只换了色和标题 | 结构层面就不同 |
| 可读性 | 字号、对比、密度、单位是否适当 | 读不下去 | 投屏/打印都清楚 |
| 反模式控制 | 是否减少无意义卡片/图标/渐变 | 满屏套路 | 每处装饰都有理由 |
| 修改成本 | 到可交付还差几轮人工修改 | 需重做 | 基本可直接用 |

评分表每格必须写一句**具体证据**（"第 4 页标题与正文同色，层级塌陷"），只打分不写证据的表格无效。

盲评要求：
- 评审者不知道作品来自 A 还是 B（用 `P01`/`P02` 匿名文件名）。
- 先看缩略图整体，再看单页；顺序随机。
- 不告诉评审者"A 组没有知识库"这类信息，避免预期偏差。
- 评审者若参与过制作，须在报告里标注，且不计入主结论。

## 6. 结论分级（只能往上用到哪一级，就说到哪一级）

| 证据情况 | 允许的说法 | 禁止的说法 |
|---|---|---|
| 只有规则文档与工作流引用 | "设计知识已接入工作流" | 任何"提升/改善" |
| 有案例展示规则被执行 | "已在这些案例中验证规则被执行" | "证明了知识库有效" |
| 受控对照、结果稳定改善（≥2 次运行、≥3 名评审或等价） | "在指定任务与模型条件下，知识库带来可观察改善" | "通用地提升 AI 设计水平" |
| 多模型 + 多任务 + 多媒介重复验证 | 才可讨论更一般的结论 | "保证专业设计" |

**禁止越级宣传**：证据不足时不得写"显著提升""全面改善""让 AI 有审美"。

## 7. 报告必须包含（缺一项即为不完整）

1. 三份任务原文与输入素材清单
2. 模型与工具版本（含 `git commit`）
3. A/B 两组完整设置与已知偏差（例如无法做到干净会话）
4. 两组原始产物（deck.json / pptx / preview / qa.json / copy.json）
5. 评审者数量、身份类型、是否知情
6. 评分分布（每维度均值 + 极差）与评语原文
7. 人工修改轮数或修改时间
8. 失败案例（哪一版更差、差在哪）
9. 结论适用范围（任务类型、模型、页数区间）
10. 尚不能证明的内容

## 9. 失败与异常时怎么办

| 情况 | 处理 |
|---|---|
| A 组被污染（读了知识库） | 该轮作废，重跑；报告里记录作废原因 |
| 两组人工修改量差异过大 | 单独列出修改轮数，作为独立维度讨论，不混进"质量"结论 |
| 评审者分歧极大（同维度极差 ≥3） | 增加评审者或复评；结论只写"评审分歧大" |
| 知识库组没有稳定优势 | **不许改结论口径**，改为定位问题：检索没命中？规则太空？模型不遵循？工具没实现？评估方法不公平？ |
| 无法凑够评审者 | 降级为"单评 + 作者自查"，并明确标注证据等级不足 |

## 检查清单

- [ ] 两组的唯一差别是知识库，其余逐项对齐并写进报告。
- [ ] A 组确实是"干净会话"，不许由作者口头保证，要有可核查记录。
- [ ] 每份任务至少 2 次运行，或明确写明"单次运行"。
- [ ] 盲评用匿名文件名，映射表与评分表分开保存。
- [ ] 每个评分格都有具体证据，不是纯数字。
- [ ] 结论用词没有超过第 6 节对应的等级。
- [ ] 报告含失败案例与"尚不能证明的内容"。
- [ ] 结果目录命名符合第 8 节，历史结果不被覆盖。
