# ADR 模板：架构决策记录

> 用途：凡是改动**核心架构、支持媒介范围、知识库治理规则、阶段顺序与版本序列**，都要留一条 ADR。
> 依据：`docs/lighthouse-plan.md` §13；治理流程见 `docs/governance.md`。
> 存放：`docs/decisions/ADR-<三位编号>-<短标题>.md`，编号只增不减。

复制下面整段，改成本次决策。

---

## ADR-001：决策标题（一句话说清改什么）

- **日期**：YYYY-MM-DD
- **状态**：提议 / 已接受 / 已废弃 / 被 ADR-XXX 取代
- **提出人**：
- **背景**：当前遇到的具体问题是什么？有没有数据或案例说明它必须现在解决？
- **目标**：本次决策服务于 `docs/lighthouse-plan.md` 的哪一条核心原则（P1–P7）？
- **方案**：具体准备怎么做？涉及哪些文件、目录、脚本、命令？
- **备选方案**：考虑过什么？为什么没选？（没有备选说明"其实没做判断"）
- **影响**：影响哪些媒介、知识条目、脚本、阈值、既有案例与文档？
- **风险**：可能引入什么问题？触发条件是什么？
- **验收**：怎么判断这次决策有效？可执行的命令或可核对的文件是什么？
- **回滚**：如果失败，怎么退回？退回后旧产物还能不能用？
- **证据**：相关案例、测试输出、讨论链接、PR 编号

---

## 填写要求

**触发条件**：要改核心架构、支持媒介范围、知识库治理规则、阶段顺序或版本序列时。

**具体动作**：
1. 先写"背景"与"目标"两段，写不出来就说明这次改动没有理由，先不做。
2. "备选方案"至少写一个真的考虑过的选项，不许写"没有其他方案"。
3. "验收"必须是可执行命令或可核对文件，不许写"效果良好"。
4. 落盘后，在 `docs/decisions/` 的索引表里加一行（编号 / 标题 / 状态 / 日期）。
5. 决策被执行后，把状态改为"已接受"并补上证据路径；被推翻时改为"被 ADR-XXX 取代"，不删除原文。

**常见错误**：
- 先做完再补 ADR（等于事后编理由，失去记录价值）。
- 只写方案不写备选与风险，导致后来者无法判断当时的取舍。
- 把"验收"写成"人工看一眼觉得可以"——那是复核，不是验收判据。
- 同一件事开两条 ADR 且互相矛盾，没有标注取代关系。

## 检查清单

- [ ] 编号唯一且递增，文件名与标题一致。
- [ ] 背景写的是具体问题，不是抽象愿望。
- [ ] 目标对应到 P1–P7 中的至少一条。
- [ ] 备选方案至少一条，并写明未选理由。
- [ ] 验收项是可执行命令或可核对文件。
- [ ] 回滚方案写清了旧产物是否仍可用。
- [ ] 已在 `docs/decisions/README.md` 索引表中登记。
