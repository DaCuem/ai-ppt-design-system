# 案例 A：工程评审 · GW-4200 边缘网关散热方案评审

11 页技术方案评审稿，用于验证本仓库的 `schema/deck.schema.json` 能承载**深底 + 等宽字体 + 表格与图表为主**的工程文档体系，并与 [`demo/`](../../../demo/README.md) 的纸感浅色体系形成对照。

> 案例内容为演示用途的虚构样本，数字不对应任何真实项目。

## 一、受众与场合

| 项 | 内容 |
|---|---|
| 受众 | 结构与散热组、声学、供应链、项目经理，约 12 人；其中 3 人当场拍板资源 |
| 场合 | DVT 前的内部方案评审会，会议室投屏 + 线上同屏，观众距屏 3–8 m |
| 时长 | 20 分钟讲 + 15 分钟讨论；11 页对应约 1.8 分钟/页 |
| 目的 | 让评审会就「是否允许进入 DVT」给出 CONDITIONAL PASS，并当场拍板三项资源决策 |
| 交付 | `build/deck.pptx`，PDF 由使用方自行导出（本机无 Office，未在 PowerPoint 中打开验证） |

## 二、风格选择理由

| 决策 | 理由 |
|---|---|
| 深底 `#0B1420` + 浅字 `#EAF1F8` | 会议室投屏以翻页为主、单页停留 60–120 s；深底把注意力压到读数与曲线，减少白底反光 |
| 数据与命令行用 Cascadia Mono | 71.3、2.14 K/W、GATE 日期等需要逐位比对，等宽让小数点与单位对齐 |
| 表格与原生 chart 占 4 页（s04/s05/s07/s08） | 评审要判「哪一版能过」，必须给出可比的三行方案表与两条曲线，而不是形容词 |
| 每页元素 5–13 个、字数 91–198 | 高于 demo 的 5–10 个元素；工程评审允许更高密度，但每页仍只留 1 个视觉焦点 |
| 单一强调色 `#6FD8FF` + 警示色 `#F2B33D` | 强调色只出现在结论、判据与超标项；超标读数（40.3）用警示色，与其余读数区分 |

与 demo 的差异是刻意的：demo 用 `#F5F2EA` 纸底 + 衬线标题 + 大面积留白，本案例用深底 + 无衬线 + 表格化。两套体系共用同一份 schema、同一套 30 项检查，说明 tokens 换色换字即可切换风格，不必改版式代码。

## 六、复用给下一个工程评审稿的三条约束

**约束 1：读数页的判定线必须与结论同页出现**

**触发条件**：页面出现 `role: kpi` 的读数（温度、余量、噪声、热阻）。
**具体动作**：在同一文本块内补一行判据，写明判定线来源（如「判定线 78.1 ℃ = TJ 105 ℃ × 0.744 降额」），来源行用 `role: source`。
**常见错误**：只放 71.3 与一个红色数字，评审会问「78.1 哪来的」，当场答不出就退回重审。

**约束 2：每页只留一个 72 pt 以上的数字**

**触发条件**：同一页出现两个及以上 `role: kpi` 元素。
**具体动作**：超标项用 `warn` 色区分，其余读数降到 72 pt 以下的同一档；三栏卡片时把最强证据放中间或最右。
**常见错误**：三个读数都用 72 pt 且同色，读者不知道先看哪个，页面的视觉焦点就消失了。

**约束 3：表格行高按内容算，不按等分给**

**触发条件**：`table` 元素某一列文字可能折行（如「处置」「触发条件」列）。
**具体动作**：`table.h` ≥ 行数 × 单行高，13 pt 单行取 0.28 in、双行取 0.55 in；给不足时行会被文字撑高、越过元素框下沿。
**常见错误**：5 行表按 3.2 in ÷ 5 = 0.64 in 硬分，其中一行折成两行后整表下移 0.2 in，压住下方结论行。
